VEREDICTO EJECUTIVO
-------------------

La pila local SI esta funcionando en lo basico: frontend, API y PostgreSQL estan
activos; el frontend y Swagger responden; la API informa estado saludable; el
login de operador y administrador funciona; PostgreSQL esta saludable y Alembic
esta en la revision head. Pytest paso 9 pruebas y el build de React/PWA termino
correctamente.

Eso NO significa que todos los requerimientos esten completos. La interfaz
actual ofrece principalmente captura de recepciones. La brecha mas importante
es que una transformacion no crea un lote de salida inventariable vinculado al
lote de entrada, por lo que no se puede demostrar la cadena completa de
trazabilidad. Tampoco se hizo un ensayo de red realmente desconectada, un
reinicio completo para probar persistencia, o los 15 casos manuales del reto.

Se evitaron escrituras en la base PostgreSQL activa y no se reiniciaron sus
contenedores para no alterar el entorno ni interrumpir posibles datos del
equipo. Por eso, los resultados de una recepcion y de persistencia despues de
reinicio se apoyan en pruebas automatizadas/configuracion, no en una nueva
operacion escrita en esa base.

2. ESTADO DE CADA REQUISITO
--------------------------

Estados utilizados:
- VERIFICADO: existe implementacion y se obtuvo evidencia automatizada o
  respuesta en vivo suficiente para el criterio indicado.
- PARCIAL: existe parte de la implementacion, pero falta funcionalidad o
  evidencia requerida.
- PENDIENTE: no hay implementacion/interfaz suficiente o no se pudo demostrar.

RF01 - Recepcion de lotes: VERIFICADO EN API; FALTA ENSAYO DE CAMPO EN VIVO.
La API guarda el productor a traves de la finca, origen, fecha, cantidad y
unidad kg; asigna un codigo de lote y rechaza cantidad cero o negativa. Pytest
verifica recepcion y cantidades invalidas. La unidad de captura actual esta
fijada a kg, no permite seleccionar otras unidades.

RF08 - Inventario disponible: PARCIAL.
La transformacion comprueba la existencia, bloquea la fila en PostgreSQL,
actualiza recibido/consumido/disponible y registra el movimiento. No hay prueba
de transformacion que demuestre el rechazo por stock insuficiente ni el reenvio
idempotente de una transformacion sin doble consumo. La idempotencia probada
en esta suite corresponde a recepciones.

RF02 - Transformacion: PARCIAL; BRECHA PRINCIPAL.
Se registra etapa, responsable, fecha, lote de entrada, cantidades e incidencia.
La salida se guarda como output_code en la transformacion, pero no se crea un
nuevo Lot con su propio saldo ni un movimiento de produccion enlazado. Sin ese
lote de salida no se puede transformar la salida en otra etapa ni reconstruir
una genealogia completa de producto a origen.

RF04 - Alertas para decidir: PARCIAL.
La API devuelve alerta de merma superior al 15% y alerta de costo unitario con
regla y causa. Pytest comprueba merma de 20% y que exactamente 15% no active la
alerta. Faltan alertas por registro incompleto y retraso. La interfaz React no
consulta ni muestra estas alertas, y no existen transformaciones en la base
activa para ensayar una alerta real en pantalla.

RF05 - Indicador economico: PARCIAL.
El servicio calcula costo unitario, margen, formula y costos incluidos. La
interfaz actual no tiene una pantalla economica donde esas cifras, unidades y
supuestos sean visibles.

RF12 - Balance economico completo: PARCIAL.
El calculo de backend devuelve costo unitario y margen sobre venta; evita
division por cero devolviendo null si salida o precio no permiten el calculo,
y explica que solo incluye costos de etapa informados. Falta prueba automatizada
del ejemplo oficial (20.000 COP/kg y margen 20%) y falta mostrarlo en interfaz.

RF06 - Ficha comercial: PARCIAL.
Existe endpoint publico por codigo y un esquema de respuesta con lista blanca
de campos, que excluye costos internos y contacto privado. Falta una pagina
publica navegable o QR. Como la base activa tiene cero transformaciones, no se
pudo verificar una respuesta de producto real ni el comportamiento visual del
estado bloqueado.

RF09 - Estado del producto: PARCIAL.
El backend acepta pendiente/liberado/bloqueado, requiere motivo y limita el
cambio a administradores. Pytest verifica 403 para operador y 200 para admin;
la API publica incluye el estado. Todavia no se demuestra que un producto
bloqueado no pueda venderse, porque no hay flujo de ventas. Ademas, la
transformacion debe rechazar explicitamente lotes de entrada bloqueados; esa
validacion no aparece en el servicio actual.

RF10 - Auditoria minima: PARCIAL.
Recepciones, consumos y cambios de estado crean eventos con actor, fecha,
accion y valores anterior/nuevo. Existe consulta de auditoria para lotes. No se
probo toda la cobertura y el modelo/base de datos no impide tecnicamente que un
administrador de DB modifique o borre filas; falta probar la proteccion del
historial en el nivel que decida el equipo.

RF07 - Persistencia: PARCIAL.
Compose configura volumen PostgreSQL y el servicio API esta activo con Alembic
en head; los datos existen ahora en PostgreSQL. No se reinicio la pila para
comparar registros antes/despues, pues la base activa puede contener datos del
equipo. Falta realizar ese ensayo en una base desechable con datos sinteticos.

RF11 - Consulta y exportacion: VERIFICADO EN API; FALTA INTERFAZ.
La consulta filtra por origen y estado; la descarga CSV en vivo devolvio HTTP
200 con las columnas solicitadas. Los endpoints estan protegidos para
administrador. La interfaz React no incluye filtros ni boton de exportacion.

Condicion tecnica de accesos: VERIFICADA PARA LAS ACCIONES PROBADAS; COBERTURA
PARCIAL DEL SISTEMA.
Las dependencias de FastAPI aplican roles en el backend; Pytest confirma que
operador no cambia estado y que admin si puede. En vivo, operador recibio 403
al consultar alertas de administrador. Falta revisar todas las rutas y vistas
protegidas al agregar nuevas pantallas.

Diferenciador offline: IMPLEMENTADO PARCIALMENTE; NO ENSAYADO SIN RED REAL.
IndexedDB mantiene fincas/recepciones y la app tiene estados de sincronizacion,
reintentos y pausa manual. El service worker se compila y sus archivos son
servidos. La pausa de sincronizacion solo retiene envios a proposito; no
demuestra que el dispositivo carezca de acceso a la API. Falta abrir la PWA de
produccion, desconectar realmente la API/red, capturar, recargar y sincronizar
una sola vez despues de reconectar.

3. PROXIMOS PASOS EN ORDEN
-------------------------

PASO 1 - Completar la relacion de transformacion (prioridad maxima).

1. Definir como un registro de salida se convierte en un Lot de producto
   procesado, con codigo, tipo/unidad, cantidad y estado.
2. Guardar la relacion entre transformacion, lote de entrada y lote(s) de
   salida. La regla del alcance permite una entrada de lote por operacion; no
   perder origen al crear la salida.
3. Crear el movimiento de consumo de entrada y el movimiento de produccion de
   salida dentro de una sola transaccion.
4. Hacer que GET de trazabilidad funcione desde el lote de entrada y desde el
   producto de salida.
5. Agregar pruebas para recepcion 100 kg -> transformacion 80 kg -> saldo,
   movimiento, merma y trazabilidad que conduce a la finca original.

PASO 2 - Cerrar inventario, idempotencia y estados.

1. Probar transformacion mayor al disponible; debe devolver error y no dejar
   movimientos, costos, auditoria ni productos parciales.
2. Reenviar la misma transformacion con la misma clave; debe dejar un unico
   consumo. Reenviar la clave con otro payload debe tener respuesta definida.
3. Probar llamadas concurrentes en PostgreSQL y confirmar que el saldo nunca
   sea negativo.
4. Impedir transformacion/venta de lotes o productos bloqueados. Definir que
   significa bloqueo para lote de materia prima y producto procesado.

PASO 3 - Agregar pantallas de los requisitos funcionales.

Crear UI para inventario y filtros/CSV de administrador; alertas con regla y
causa; calculo economico con formula/unidades/supuestos; ficha publica por
codigo y estado; y cambios de estado solo para administrador. Mantener la
validacion de permisos en backend aunque el frontend oculte acciones.

PASO 4 - Hacer ensayos controlados de persistencia y offline.

- Usar base PostgreSQL de prueba, crear datos sinteticos, guardar conteos/codigos,

- No usar la base persistente de demostracion para pruebas que la ensucien.

4. CRITERIO PARA DECIR “ESTA LISTO”
----------------------------------

No marcar un RF como completo solo porque existe una ruta o una funcion. Para
cada uno conservar: implementacion, prueba automatizada/manual, resultado
observado y, si requiere UI, recorrido visible en navegador. Para el nucleo del
reto se debe poder demostrar:

finca/productor -> recepcion -> lote de entrada -> transformacion -> lote de
salida -> saldo y costos -> consulta de trazabilidad -> ficha/estado publico.

El siguiente objetivo del equipo deberia ser completar esa cadena y probarla en
un conjunto aislado de datos. Luego se puede cerrar la prueba offline real y
preparar la evidencia para el jurado.

ACTUALIZACION - RELACION DE TRANSFORMACION (15 DE OCTUBRE DE 2026)
-------------------------------------------------------------------

Se completo el siguiente paso priorizado despues de esta revision. El endpoint
POST /api/v1/transformations ahora materializa cada salida positiva como un
lote de producto con codigo, tipo, unidad, cantidad, saldo y estado pendiente.
Acepta el formato anterior de salida unica y una lista de salidas. Solo admite
un lote de entrada por operacion, y cada salida hereda finca, productor y origen.

La tabla transformation_outputs enlaza cada salida con su transformacion. En
la misma transaccion se guardan consumo de entrada, nuevos lotes, movimientos
de produccion, costo y auditoria. La idempotencia hace que repetir la misma
operacion no vuelva a consumir stock. GET /api/v1/lots/{id}/traceability
recorre origenes y productores hacia atras, y productos descendientes hacia
adelante. Las salidas son tambien consultables individualmente en la ficha
publica por codigo.

Se agrego la migracion Alembic c2a7f4b89d10. Ademas de incorporar product_type
y transformation_outputs, convierte las salidas positivas de transformaciones
historicas en lotes y movimientos de produccion, conservando su origen. La
migracion NO se ejecuto contra la base PostgreSQL activa.

Verificacion automatizada actualizada: python -m pytest -q desde backend/;
12 pruebas aprobadas y una advertencia de deprecacion TestClient/HTTPX. Se
prueba el caso 100 kg -> 80 kg, el saldo de ambos lotes, movimientos,

ACTUALIZACION - INVENTARIO, IDEMPOTENCIA Y BLOQUEOS (15 DE OCTUBRE DE 2026)
--------------------------------------------------------------------------

Se completo la verificacion automatizada del Paso 2:

- Una transformacion que excede el disponible devuelve HTTP 409. La prueba
  comprueba que no quedan transformacion, salida, movimiento, costo o auditoria
  parcial y que el saldo inicial no cambia.
- Repetir la misma clave y el mismo payload devuelve el mismo resultado sin
  otro consumo. Reutilizarla con campos distintos devuelve HTTP 409. Se guarda
  una huella SHA-256 persistente en `request_hash`; se agrego la revision Alembic
  d843a91c5e2b.
- La prueba de carrera PostgreSQL se ejecuto contra un contenedor PostgreSQL 16
  desechable y una base/schema de prueba aislados, sin volumen persistente. Dos
  consumos concurrentes de 7 kg contra 10 kg dieron un exito y un HTTP 409; el
  saldo final fue 3 kg. El contenedor temporal se retiro al terminar.
- Solo administradores pueden bloquear o liberar lotes con motivo. Un lote de
  materia prima bloqueado conserva saldo e historial pero no se puede consumir
  hasta liberarlo. Un producto procesado bloqueado tampoco se puede transformar
  y su ficha publica muestra estado `blocked` y disponibilidad
  `not_available`; solo `released` se considera disponible.
- No existe aun un endpoint de ventas. Por eso no hay despacho que permitir o
  rechazar; si se implementa, debe exigir estado `released` en backend.

Resultado total actual desde backend/: `python -m pytest -q` da 14 aprobadas y
1 omitida (la prueba PostgreSQL se omite en la suite normal si no se configura
`TEST_POSTGRES_URL`). La prueba PostgreSQL se ejecuto por separado y paso. Sigue
pendiente migrar una base PostgreSQL persistente de ensayo y hacer el recorrido
manual completo de UI. No se aplicaron migraciones ni escrituras a la base
activa del proyecto.
